## Executive Finding

There is a proven importer/exporter version split.

1. Current repository code (contract introduced by commit
   `f398e8d1ebf8b78787c12eec65d7f50bd9c9e7a4` on 2026-07-25) accepts only one
   exact 29-column CSV header in exact order.
2. The local workbook
   `source-files/Production Orders (Marco) V14.07.xlsm` contains an embedded
   `ExportValidation.bas` module whose `ExportSelectedExtrusionOrdersCsv`
   still writes the obsolete 26-column
   `quantity_1/unit_1/quantity_2/unit_2/extrusion_flag` format.
3. Therefore, a CSV generated by that embedded V14.07 macro is deterministically
   rejected by the current importer before any data row is processed.
4. Production was subsequently migrated and deployed to `95093c0` on July 28,
   2026. That revision uses the strict 29-column importer. The durable evidence
   is `v2-files/MIGRATION-REPORT-2026-07-28.md`.
5. Therefore the known production pairing is current 29-column app plus the
   obsolete 26-column exporter embedded in the inspected V14.07 workbook. If
   diagnosing a different server instance, fingerprint it first through
   `/health` and `/admin/import-template.csv` rather than assuming it matches
   production.

This explains why files from both generations may appear to be “not accepted”
when the workbook macro, app checkout, and deployed app are not aligned.

The exact rejected user file and the exact target-server import message were not
provided during this investigation. The version mismatch above is directly
proven and is the deterministic root cause when the inspected V14.07 embedded

## CSV Transport Contract

### Required/recommended physical format

- Upload a CSV text file, not `.xlsx` or `.xlsm`.
- Use comma `,` as the delimiter.
- Use normal CSV double-quote escaping.
- Recommended encoding: UTF-8 with BOM, matching the workbook macro and known
  Shift Manager exports.
- UTF-8 without BOM is also accepted and covered by repository tests/fixtures.
- CRLF and LF record endings are both accepted and covered by actual files/tests.
- Do not add a `sep=,` preamble; it becomes the header and is rejected.
- Do not use semicolon-delimited regional CSV output; there is no delimiter
  sniffing.
- Do not use UTF-16 “Unicode Text” output.

### Exact decoder behavior

`app/importer.py:362-369` tries, in order:

1. `utf-8-sig` (UTF-8, stripping one leading UTF-8 BOM);
2. `cp1251`;
3. `latin-1`.

UTF-8 with or without BOM and CP1251 are therefore intentionally decodable.
`latin-1` is a last-resort byte-preserving fallback, not the recommended export
format. UTF-16 typically decodes into NUL-containing/gibberish headers and will
fail header validation.

### Server upload behavior

The browser input has `accept=".csv,text/csv"`, but this is a client hint only.
The FastAPI route reads the complete upload and adds no explicit importer-level
validation for filename extension, MIME type, file-size limit, or workbook
version beyond any framework/server limits. A binary Excel file can therefore
reach the CSV parser and fail with a confusing header error. Always confirm the
uploaded artifact itself is CSV text.

The filename is used only for import-history display/storage. It does not select
a parser version.

### Quoting rules

Use standard CSV quoting:

- field containing comma: `"20,000"`;
- field containing a quote: double the quote inside a quoted field;
- field containing CR/LF: enclose it in double quotes;
- a decimal comma such as `1250,5` must be CSV-quoted because comma is the
  delimiter: `"1250,5"`.

The importer uses Python `csv.DictReader` with the default Excel dialect. There
is no delimiter/dialect sniffing.

### Data-record width edge behavior

The contract requires one value position per header field. However, the current
implementation does not explicitly validate each data row's field count:

- missing trailing values become blank strings;
- extra data values beyond the 29 header fields are placed by `DictReader`
  under a `None` key and ignored by `normalize_row()`;
- an unquoted comma can therefore shift fields and may cause misleading row
  validation or, worse, incorrect stored data rather than a clean width error.

Do not rely on this permissiveness. The exporter must quote correctly and emit
exactly 29 logical values per record. A future hardening task may add explicit
row-width rejection, but that would be a behavior change and is not part of
this report.

## Exact Current Row Validation

All cell values are converted to strings and stripped of leading/trailing
whitespace by `app/importer.py:404-415`. Internal whitespace is generally
preserved. Recipe parsing additionally normalizes whitespace inside its parsed
category/material representation while preserving the imported source text
after outer trimming.

Validation order for each data row is:

1. Increment `rows_seen`; CSV physical header is row 1, so the first data row is
   reported as row 2.
2. Normalize the 29 values.
3. If `order_number` is blank: skip with `Липсва номер на поръчка.`
4. If `extrusion_sequence.strip() != "1"`: skip with
   `Пропуснат ред: няма екструдиране.`
5. If the same normalized order number already appeared in an earlier eligible
   row in the same CSV: skip as an in-file duplicate.
6. Resolve an existing card by order number, including the saved import-source
   order number.
7. If an existing card is found and overwrite is not checked: skip it as an
   existing duplicate.
8. If overwrite is checked, block a stale overwrite that would replace an
   administrator correction made since the saved import-source baseline.
9. For overwrite of a card whose status is no longer `imported`, validate the
   incoming recipe and positive gross against release requirements before
   changing the active/completed card.
10. Apply strict import recipe validation.
11. Insert a new imported card or update only imported/source fields on the
    existing card.

`extrusion_sequence` accepted examples after cell trimming:

```text
1       accepted
 1      accepted after trimming
1       accepted when Excel supplies it as normal displayed text
01      skipped
1.0     skipped
Да      skipped
TRUE    skipped
blank   skipped
2       skipped
```

There is no app-side type/date validation for other non-recipe source values at
new-draft import time.

`order_number` duplicate matching is exact text matching. It is not normalized
as a number. For example, `00123` and `123` are different strings, as are
case-different text identifiers under the current Python/in-database exact
comparison behavior. The workbook exporter should provide the canonical
business identifier consistently rather than exploiting this distinction.

## Exact Recipe Grammar at Import

Recipe source fields are the seven fields from `raw_material_a` through
`chalk`. `packaging_method` is not a recipe field.

If all seven recipe fields are blank, the current importer accepts the row as an
unreleased draft. Release will later fail because a complete 100% recipe is
required.

If any recipe field is nonblank, every nonblank recipe cell must have this
shape:

```text
Category; Material name | Percent%
```

Examples:

```text
LDPE; Rompetrol Midilena B20/03 | 77%
LLDPE; SABIC 119ZJ | 18%
Antistatic Additive; Novachem AT 04673 LD | 2%
White Masterbatch; Polibach White 8000 ET | 3%
```

Import parser rules from `app/recipe_parser.py` and
`app/importer.py:335-359`:

- `|` is mandatory; parsing splits on the final `|`.
- Exactly one `;` must occur in the identity text before the final `|`.
- Category before `;` must be nonblank.
- Material after `;` must be nonblank.
- A second semicolon is rejected. Category and material names therefore cannot
  contain `;` in the pilot contract.
- Material text may contain an earlier `|`; only the final pipe separates the
  percent.
- Percent must end with `%`.
- Numeric percent grammar is `digits`, optionally followed by `.` or `,` and
  one or more fractional digits.
- Leading `+`/`-`, exponent notation, thousands separators, `.5`, and `,5` are
  not accepted by the recipe percent grammar.
- Dot and comma decimal separators are accepted (`2.5%`, `2,5%`).
- Whitespace around delimiters and before `%` is tolerated.
- Each populated percentage must be greater than zero.
- All populated recipe percentages across all seven fields must sum exactly to
  Decimal `100`.
- If any cell-level parse error exists, the parser reports those errors without
  adding a second total error.
- The app does not validate category names or material names against the Excel
  recipe catalog. Excel/tooling owns catalog validity.

Typical current import error prefix:

```text
Рецептата не може да бъде импортирана: <field/reason>. Коригирайте рецептата и опитайте отново.
```

Representative reasons:

```text
липсва разделител |
липсва разделител ;
липсва категория
липсва материал след категория
неподдържан разделител ; в материала
липсва процент
невалиден процент
процентът трябва да е по-голям от 0%
сборът на процентите трябва да е точно 100%
```

Recipe row failure is isolated to that row. Valid rows in the same CSV still
import and persist.

## Import Acceptance Versus Release Acceptance

Do not conflate import with release to a machine.

For a new card:

- `order_number` plus `extrusion_sequence == "1"` are the non-recipe row-level
  requirements for import.
- Blank extrusion detail fields are allowed at import.
- All recipe fields blank are allowed at import.
- `ordered_gross_kg` may be blank/invalid at import.

Before release:

- machine assignment is required;
- queue target position is required;
- `ordered_gross_kg` must parse as a finite positive decimal;
- recipe must parse and total exactly 100%;
- an all-blank recipe fails release.

Gross parsing before release strips outer whitespace, changes comma to dot, and
uses Python `Decimal`. Values such as `1250.5` and `1250,5` are valid (the latter
must be quoted in CSV). Blank, zero, negative, `NaN`, `Infinity`, or text with a
unit such as `1250 kg` fails. `ordered_rolls`, `ordered_meters`, and
`ordered_units` never substitute for gross kilograms.

Unlike recipe percentages, gross parsing does not use the recipe percent
regular expression. Executable behavior follows Python `Decimal`; for example,
positive finite exponent text such as `1E3` can pass the app release parser even
though the intended workbook export should emit ordinary decimal text.

Overwrite of a card already beyond `imported` status is also subject to release
validity so that re-import cannot make an active/produced card invalid.

## Duplicate and Overwrite Semantics

An import can be structurally accepted while every row is skipped.

### Duplicate in the same CSV

After the first eligible occurrence of an `order_number`, later occurrences in
the same file are skipped with:

```text
Дублиран номер на поръчка в този CSV файл.
```

The first occurrence wins. The duplicate is not used as an update.

### Order already in the app

With the overwrite checkbox clear, an existing order is skipped with a message
that instructs the shift manager to select update/overwrite. This is not a
header failure.

With overwrite selected:

- only the 29 imported/front-card source fields are updated;
- roll entries, gross/net weights, roll tare snapshots, current tare, pallets,
  timing segments, lifecycle status, assignment/queue, rewinding state, shift
  attribution, and operator actual-material/batch data are preserved;
- card version increments;
- normalized recipe components are refreshed from the source recipe;
- a stale incoming row that would replace a post-import admin correction is
  blocked for explicit review;
- if the incoming value matches the current administrator-corrected value, the
  overwrite may proceed and establishes a new import-source baseline.

The 71-row known-good later CSV imports 71/71 into a clean database. If those 71
order numbers already exist in the target database and overwrite is not
checked, a result of 0 imported / 71 skipped is expected and does not mean the
CSV schema was rejected. Read the per-row result table.

## How to Read the Admin Import Result

The `/admin/import` page reports:

```text
<rows_imported> imported
(<created> new, <updated> updated),
<skipped> skipped from <rows_seen> rows
```

Use these distinctions:

| Observation | Meaning |
| --- | --- |
| `rows_seen == 0`, one result row labelled as file/blocked | Header or empty-file failure; no batch persisted |
| `rows_seen > 0`, some rows created and some blocked/skipped | File header accepted; investigate row messages |
| `rows_seen > 0`, all `няма екструдиране` | `extrusion_sequence` is not exact `1` in each row, or columns shifted from bad quoting |
| all existing-order messages | Header accepted; duplicate behavior, not format rejection |
| recipe-specific blocked rows | Header accepted; inspect `AH:AN` output and percentage total |
| stale administrator-correction message | Header accepted; overwrite conflict protection is working |

Successful POSTs and row-level result batches redirect to
`/admin/import?batch_id=<id>`. File-level header failures stay on the POST
response because no batch ID is created.
